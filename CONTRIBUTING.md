# Contributing

These rules apply to every contributor, human or AI. How to build is in the
[README](README.md#building-the-repository).

This repository proves that Pico's RV64IM chips implement the RISC-V specification. A wrong
definition or an unreviewed hypothesis makes a proof say less than it appears to, so every change
must be justified by its source and checked before it is merged.

## The bar

- Read the Pico source of the chip, the existing Lean files and the specification before writing.
- Every constraint, column and bus message you describe has a source: cite the Pico file and line
  at the pinned commit.
- If the source is ambiguous, or the Rust and the extracted constraints seem to disagree, stop
  and say so in the issue. Do not pick a reading silently.
- Never claim a check passed unless you ran it and saw it pass.
- One idea per pull request: one chip, one opcode group, or one piece of infrastructure.

## Branches

`main` holds the reviewed results. The move to Pico v3.1.1 happens on `pico-v3`: chip and
framework pull requests target `pico-v3`, which merges into `main` once every chip has moved.

## Layout and ownership

```text
PicoFV/Fundamentals/                    shared infrastructure            framework
PicoFV/RV64IM/Extraction/               generated by extractor/          framework (never edited by hand)
PicoFV/RV64IM/RVSail/, Transpiler/      RISC-V glue and the bus contract framework
PicoFV/RV64IM/{Airs,Constraints,Spec}/  one set of files per chip        the chip's owner
PicoFV/RV64IM/Equivalence/              opcode equivalence theorems      the opcode group's owner
extractor/, scripts/, .github/          tooling and CI                   framework
```

A chip's files may import the shared layers, gadgets and the chip's own files, but never another
chip; `scripts/fv-check/check_layers.sh` enforces this. A change to a framework file, above all to
the bus contract in `RVSail/Buses.lean`, goes in its own pull request, never inside a chip's.

## Moving a chip to the pinned Pico

1. Regenerate its file with `extractor/`, and remove it from `extractor/pending.txt`.
2. Update the chip's `Airs/` layout and `Constraints/` restatement to the new constraints.
3. Repair the chip's `Spec/` proofs, and the equivalence proofs that use it.
4. If a proof needs a new or stronger hypothesis, or a constraint looks too weak to prove the
   specification, stop and report it in the issue before going further. It may be a soundness
   gap in Pico.

## Proofs

- No `sorry`, `admit` or new `axiom` declarations. An `axiom` makes Lean accept a statement
  without proof, so one could prove anything. `check.sh` fails when a checked theorem depends on
  an axiom outside the allowed lists.
- No new `native_decide`, `bv_decide` or `decide +native`; they trust compiled code. `check_tactics.sh` fails when
  a file uses them more often than the baseline. Removing uses is welcome: record it with
  `check_tactics.sh --update`.
- A change to a theorem statement shows up as a diff of `scripts/fv-check/signatures.txt`. Point
  it out in the pull request, say why, and record it with `check.sh --update` only once reviewed.
- Name new theorems by the [Mathlib conventions](https://leanprover-community.github.io/contribute/naming.html).

## Checks

Run these before opening a pull request, and list them with their result in its description:

```bash
lake build PicoFV64
scripts/fv-check/check.sh
scripts/fv-check/check_layers.sh
scripts/fv-check/check_tactics.sh
python3 scripts/fv-check/soundness_facts.py --check
(cd extractor && cargo run --release -- --check ../PicoFV/RV64IM/Extraction)
```

If a check's facts change (for example a file leaves `pending.txt`), regenerate `SOUNDNESS.md`
with `python3 scripts/fv-check/soundness_facts.py`.
